# FilteredImage — как устроен фильтр изображений

Изображение в духе fumadocs.dev: `pixel` (пикселизация), `dither` (упорядоченный дизеринг по матрице
Байера на палитре темы) и `ascii` (символы моно-шрифта по яркости) — шаги 1–9. С шага 10 — ещё 16 режимов
на рантайме эффектов `@haunt/ui/fx`: диффузия ошибки, растр, дуотон, Брайль, табло, CRT, сдвиг каналов,
сортировка пикселей, изолинии, Собель, тепловая карта; часть из них — шейдером WebGL2 с запасным Canvas 2D.
Для обложек и баннеров пространств, превью медиа, пустых состояний, витрины. Не для аватаров и не для того,
что нужно разглядеть.

```tsx
<FilteredImage src={cover} alt="Обложка пространства" mode="dither" aspectRatio="21 / 7" />
<FilteredImage src={banner} alt="Баннер события" mode="halftone" options={{ shape: 'line', angle: 30 }} />
```

## Шаг 1. Разметка: картинка остаётся картинкой

Компонент рендерит обёртку, внутри — обычный `<img>` и поверх него `<canvas aria-hidden>`.

- `<img>` нужен всегда: он грузит исходник, даёт пропорции (`aspectRatio` по умолчанию — натуральные) и
  `alt` для скринридера. Когда фильтр включён, у него `opacity: 0` — из дерева доступности он не пропадает.
- При `data-effects="off"` canvas вообще не создаётся — остаётся обычное изображение с `object-fit: cover`.
  Если исходник с чужого origin без CORS, canvas «отравляется» и `getImageData` бросает — компонент ловит это
  и тоже показывает обычное изображение. Поэтому `src` — свой origin, `data:` или `blob:` (или `crossOrigin`).

## Шаг 2. Уменьшение до сетки ячеек (общий шаг всех режимов)

`render-frame.ts → sampleGrid`. Рамка W×H делится на ячейки: `cols = ceil(W / cell)`, `rows = ceil(H / cell)`
(`gridSize`, неполная ячейка у края тоже считается, иначе край пустой). Исходник рисуется в холст размером
`cols × rows` через `drawImage` с `imageSmoothingQuality = 'high'`: браузер сам усредняет все пиксели под
каждой ячейкой. Получается по одному цвету на ячейку — это и есть пикселизация, остальное — обработка этих
цветов. Перед этим холст заливается цветом фона (`--background`): прозрачные места исходника иначе стали бы
нулями — чёрным.

Часть исходника берётся как `object-fit: cover` (`coverRect`): масштаб = `max(W / w, H / h)`, лишнее
обрезается поровну с двух сторон.

**Почему через canvas, а не CSS.** `image-rendering: pixelated` умеет только «увеличить без сглаживания»; ни
палитры, ни порогов, ни символов CSS не даёт. WebGL-шейдер дизеринга был бы быстрее на кадр, но кадр здесь
считается редко (см. шаг 6), а 2D-контекст проще, не тратит GPU-контекст на каждую картинку (их у браузера
ограниченное число) и работает в тестах.

**Физические пиксели.** Для `pixel` и `dither` сетка считается в пикселях экрана: `cell × devicePixelRatio`
округляется до целого (`deviceSize`). Ячейка 3 CSS px при масштабе 125 % — это 3.75 px, и без округления
соседние ячейки выходили бы по 3 и 4 px — заметная рябь.

## Шаг 3. `pixel` — пикселизация

Сетка из шага 2 растягивается обратно на рамку с `imageSmoothingEnabled = false` (`upscale`): каждая ячейка
становится чётким квадратом своего среднего цвета. Цвета исходника не меняются. Ячейка по умолчанию 8 px.

## Шаг 4. `dither` — упорядоченный дизеринг по Байеру

**Палитра из темы.** Четыре токена `--image-dither-1…4` (блок `*` в `tokens.css`): фон, смесь акцента с
фоном, акцент, текст акцента. Они читаются на самом элементе (`read-palette.ts`), поэтому `AccentScope` и
`ThemeScope` перекрашивают кадр. Токены бывают `color-mix()` — canvas такое не разбирает, так что цвет сначала
вычисляет CSS (свойство `color` пробного `<span>` внутри элемента), а потом canvas переводит результат в байты
через один пиксель.

**Шкала краски** (`inkRamp`). Палитра сортируется по яркости и, если фон светлый, разворачивается: первым
всегда идёт цвет, ближайший к фону страницы, последним — «полная краска». Яркость исходника = количество
краски. В тёмной теме выходит позитив, в светлой — негатив, как у дизеринговых картинок fumadocs.dev в
светлой теме. Причина: в обеих темах тёмные места исходника (небо, тень, фон фото) сливаются с фоном страницы,
и картинка лежит на ней иллюстрацией, а не тёмным прямоугольником.

**Яркость** (`luminance`): `L = (0.2126·R + 0.7152·G + 0.0722·B) / 255` — веса Rec. 709 прямо на
гамма-кодированных значениях. Линейная яркость темнила бы средние тона; глаз сравнивает именно кодированные.

**Матрица Байера** (`bayerMatrix`). Строится рекурсией от `[[0, 2], [3, 1]]`:

```
M(2n) = | 4·M      4·M + 2 |        M(4) = |  0  8  2 10 |
        | 4·M + 3  4·M + 1 |               | 12  4 14  6 |
                                           |  3 11  1  9 |
                                           | 15  7 13  5 |
```

Каждый следующий порог стоит как можно дальше от предыдущих, поэтому при любой яркости точки распределены
равномерно, без сгустков. Берётся 8×8 — 64 уровня: достаточно для плавных градиентов, а узор ещё читается как
«пиксельный».

**Порог** (`ditherPixels`). Для ячейки (x, y) с яркостью L и шкалой из k цветов:

1. `v = L · (k − 1)` — положение на шкале; нижний цвет `i = floor(v)`, доля верхнего `f = v − i`;
2. порог `t = (M[y mod 8][x mod 8] + 0.5) / 64` — у каждой клетки свой, повторяется плиткой 8×8;
3. `f > t` → цвет `i + 1`, иначе `i`.

На площади 8×8 доля верхнего цвета равна `f` с точностью 1/64 — средняя яркость сохраняется (тест «доля
светлых точек повторяет яркость серого»: серый 64 из 255 даёт ровно 16 светлых точек из 64). `+0.5` ставит
порог в середину ступени: при L = 0 и L = 1 узора нет, цвет чистый. В отличие от диффузии ошибки
(Флойд — Стейнберг) узор регулярный и локальный: соседние ячейки не зависят друг от друга, нет «червей»,
а при смене размера узор не «плывёт» по всей картинке.

Результат пишется обратно в сетку (`putImageData`) и растягивается без сглаживания, как в шаге 3. Ячейка по
умолчанию 3 px.

## Шаг 5. `ascii` — символы по яркости

Ячейка — знакоместо моно-шрифта: кегль `cell` (10 px), ширина `0.6 · cell` (ширина знака JetBrains Mono),
высота строки `1.1 · cell` — плотнее текста, чтобы ряды не распадались на полосы. Сетка из шага 2 считается
с этими неквадратными ячейками, поэтому пропорции картинки не искажаются.

Набор `' .:-=+*#%@'` (`ASCII_RAMP`) идёт от пустого к плотному: каждый следующий символ закрашивает больше
площади знакоместа. Индекс символа — `round(L · 9)` (`asciiGrid`), по тому же правилу «яркость = краска», что
и у дизеринга. Символы рисуются `fillText` цветом `--image-ascii-color` шрифтом из `--font-mono` — это и есть
связь с TUI-акцентами кита. Прозрачность растёт с плотностью (0.3…1), и чтобы не менять стиль на каждом знаке,
символы рисуются группами по ступеням: десять смен `globalAlpha` на кадр. Фон не заливается — знаки ложатся
на подложку карточки.

Перед первым кадром компонент ждёт `document.fonts.load(…)`: без этого первый кадр вышел бы системным моно.

## Шаг 6. Кэш: перерисовка только при смене размера, темы или режима

- **Кадр — отдельный canvas** размером рамки × `devicePixelRatio`. На видимый холст он только копируется
  (`drawImage`), поэтому наведение и линза не пересчитывают пиксели.
- **Кэш на модуль** (`frame-cache.ts`): ключ — всё, от чего зависит кадр: режим, размер, ячейка, масштаб
  экрана, цвета палитры, шрифт, источник. Изменился вход — другой ключ, инвалидировать ничего не нужно. Одна
  обложка в списке и в превью, повторный монтаж, тема туда-обратно — кадр готовый. LRU на 24 кадра: `Map`
  помнит порядок вставки, использованный ключ переставляется в конец, вытесняется первый (кадр 1200×600 при
  масштабе 2 — около 11 МБ).
- **Когда пересчитывать.** `ResizeObserver` на обёртке (в `requestAnimationFrame`, чтобы серия изменений
  дала один кадр); `MutationObserver` на предках — `data-theme`, `data-effects` и инлайн-`--accent`
  (`fx/environment.ts`, шаг 10). Атрибут `style` меняет и прожектор (`--spot-x` на каждом движении мыши), так
  что палитру трогает только запись, где в `style` есть `--accent`.

## Шаг 7. Реакция: линза и «проявление»

**Линза под курсором** (`reveal`). По `pointermove` в `requestAnimationFrame` на холст копируется кадр, а
поверх — круг из второго кадра: оригинала (`'original'`, `renderOriginal`) или того же фильтра с ячейкой
вдвое мельче (`'finer'`). Круг вырезается на общем на все экземпляры рабочем холсте: кусок второго кадра,
затем `globalCompositeOperation = 'destination-in'` с радиальным градиентом — края растворяются. Второй кадр
считается лениво, при первом наведении, и тоже кэшируется. Сила — по уровню эффектов: `subtle` — радиус
64 px, непрозрачность 0.75; `rich` — 112 px и 1. `reveal="none"` — без линзы.

**«Проявление»** (`appear`). Когда картинка впервые попадает на экран (`IntersectionObserver`), кадры идут
с ячейкой ×6, ×4, ×2.5, ×1.6 и ×1 через 70 мс — меньше полсекунды, из крупных пикселей в обычные. Крупные
кадры дешёвые (ячеек мало) и в кэш не идут. Холст при этом проявляется через `opacity`.

## Шаг 8. Уровни эффектов и reduced-motion

| Условие                       | Что видно                                                       |
| ----------------------------- | --------------------------------------------------------------- |
| `data-effects="off"`          | обычное изображение, canvas не создаётся                        |
| `data-effects="subtle"` / нет | фильтр, проявление, линза 64 px                                 |
| `data-effects="rich"`         | фильтр, проявление, линза 112 px, оригинал проступает полностью |
| `prefers-reduced-motion`      | статичный кадр: без проявления и без линзы                      |

Уровень читается с ближайшего `[data-effects]`, а не из `useTheme`: в документации и на экранах он бывает на
контейнере. Чтение — в layout-эффекте, поэтому при `off` первым кадром сразу идёт обычное изображение.

## Шаг 9. GIF и видео: фильтр покадрово

**Почему не просто `<img>`.** `drawImage(<img>)` у анимированного GIF по спецификации рисует первый кадр —
Chromium и WebView2 так и делают. Поэтому кадры нужно достать самим.

1. **Вид источника** — `media-source.ts`, `detectMediaKind`: `gif`, `webp`, `apng` → `animated`; `mp4`,
   `webm`, `mov` → `video`; у `data:` — по MIME. PNG и AVIF не угадываются (почти всегда статичны, а проверка
   стоит повторной загрузки) — их и `blob:` передают явно: `media="animated" | "video"`.
2. **GIF → кадры** — `animated-decoder.ts`: `fetch` → `ImageDecoder` (WebCodecs) → ждём `tracks.ready` и
   `completed` → каждый кадр в `ImageBitmap` (не держим `VideoFrame`: он занимает память декодера) с
   задержкой из `duration`. Задержка < 20 мс → 100 мс, как у браузеров (`frameDelay`). Не больше 240 кадров,
   длинная сторона ≤ 960 px — фильтр всё равно уменьшает до сетки. Разобранное кэшируется на 6 адресов.
3. **Видео → кадры** — `<video muted loop playsInline>` и `requestVideoFrameCallback`: он только отмечает,
   что пришёл новый кадр, а рисует общий цикл кадров (шаг 10), не чаще 30 в секунду (`shouldSkipVideoFrame`);
   без него — каждый кадр цикла с тем же потолком. GIF тоже идёт в общем цикле: кадр меняется, когда
   прошла его задержка.
4. **Фильтр на лету.** Каждый кадр идёт через тот же `renderFrame`, но в переиспользуемые холсты
   (`FrameSurfaces`: сетка и кадр): новый canvas на кадр — десятки мегабайт мусора в секунду. Кэш кадров
   (шаг 6) для живых кадров выключен — у них нет устойчивого ключа. Линза под курсором пересчитывается тоже
   в свой холст.
5. **Экономия.** Вне экрана и на скрытой вкладке планировщик задачу не зовёт, а видео ставится на паузу
   (`onVisibilityChange` задачи). Дорогой режим на CPU пропускает кадры по бюджету (шаг 10). Во время «проявления» анимация ждёт, затем продолжается. Номер кадра GIF хранится в сцене:
   смена темы перезапускает эффект, а анимация идёт дальше с того же места.

| Условие                     | GIF / видео                                                        |
| --------------------------- | ------------------------------------------------------------------ |
| фильтр включён              | покадрово через фильтр, `data-playing` на корне                    |
| `data-effects="off"`        | обычные `<img>` / `<video>`, анимирует браузер                     |
| `prefers-reduced-motion`    | статичный первый кадр, видео на паузе — и с фильтром, и без        |
| нет `ImageDecoder` (Safari) | первый кадр через фильтр: картинка не ломается, просто не движется |

Для историй GIF собирается в коде (`lib/stories/demo-gif.ts`: палитра 6×6×6 и LZW по GIF89a), а видео
пишется из canvas через `MediaRecorder` — ничего не скачивается.

## Шаг 10. Рантайм `fx`: окружение, один цикл кадров, бюджет

Новые режимы и будущие фоны стоят на общем рантайме `packages/ui/src/fx` (вход `@haunt/ui/fx`).

**Окружение — в одном месте** (`fx/environment.ts`, хук `fx/use-fx-environment.ts`). С ближайшего предка
читаются `data-effects`, `data-fx-renderer` (принудительный путь рендера, шаг 11) и `prefers-reduced-motion`;
`MutationObserver` на всей цепочке предков ловит их смену и смену темы или акцента. JS-эффекту, который сам
решает, двигаться ли (расшифровка текста, счётчики), хватает `isMotionAllowed(element)`: уровень не `off` и
нет reduced-motion.

**Один `requestAnimationFrame` на страницу** (`fx/scheduler.ts`). Эффект подписывается
`schedule({ frame(now, dt) }, { element })` и получает кадры, пока элемент на экране (один общий
`IntersectionObserver` с запасом 64 px) и вкладка видна. Нет видимых задач — цикл стоит, пустых кадров нет.
После паузы `dt` начинается с нуля, а не с секунд отсутствия. `cancel()` — при размонтировании.

**Бюджет кадра** (`fx/frame-budget.ts`, чистые функции с тестами). Цена каждого кадра задачи меряется, и по
скользящему среднему (вес нового замера 0.25) задача пропускает кадры: среднее втрое выше её бюджета
(4 мс) — рисуется каждый третий кадр, но не реже чем раз в 8. Разовый всплеск (сборка мусора) гаснет за
несколько кадров. Сверх того весь проход ограничен 10 мс: если задачи кадра их съели, остальные идут в
следующем кадре первыми — очередь вращается, никто не голодает.

## Шаг 11. Пути рендера и WebGL2 с запасным путём

**Стратегия эффекта** (`fx/renderer.ts`) — какие пути у него есть: `{ webgl?, canvas2d?, static }`.
`pickRenderer` выбирает: сам по себе — WebGL только на GPU, иначе Canvas 2D, иначе статичный кадр.
`data-fx-renderer="webgl | canvas | static"` на любом предке задаёт путь принудительно — для историй, тестов
и отладки; недоступный путь сползает вниз (webgl → canvas → static). Путь, которым кадр нарисован на самом
деле, виден в `data-renderer` на корне. У фильтра `static` — один кадр без линзы, проявления и анимации.

**Есть ли WebGL2** (`fx/webgl/support.ts`). Наличие `WebGL2RenderingContext` ничего не значит (драйвер в
чёрном списке, GPU выключен политикой), поэтому контекст создаётся по-настоящему. Сначала — с
`failIfMajorPerformanceCaveat`, плюс проверка имени рендерера (SwiftShader, llvmpipe): программный
растеризатор помечается `software` — он рабочий, но медленнее CPU-ядер, и сам по себе не выбирается.
Результат кэшируется, а созданный контекст не выбрасывается — его забирает общий контекст.

**Один контекст на страницу** (`fx/webgl/shared-context.ts`). Браузер даёт странице около 16 WebGL-
контекстов и при превышении молча теряет самый старый — галерея фильтров упёрлась бы в лимит сразу. Пул с
вытеснением теряет контекст как раз у видимого эффекта, и пересоздание (собрать программы, загрузить
текстуры) на прокрутке шло бы пилой. Поэтому контекст один, на холсте вне DOM: эффект рисует в него проход и
тут же копирует результат в свой 2D-холст (`drawImage`, в ту же задачу — буфер ещё не отдан композитору).
Программа собирается один раз на страницу. Холст растёт только вверх (до 4096), проход занимает его левый
нижний угол — начало координат GL снизу. Кадр шейдера копируется в свой холст `FrameSurfaces.shader`: у
холстов CPU-пути контекст с `willReadFrequently` живёт в памяти CPU, и копия туда стоила бы чтения с GPU.

**Обёртка без three.js** (`fx/webgl/gl.ts`): полноэкранный треугольник из `gl_VertexID` (без буферов, пустой
VAO), uniforms по типам из самой программы (`getActiveUniform` — не нужно писать `uniform3fv` руками),
текстуры из `ImageBitmap` / canvas / `<video>` / `<img>` в переиспользуемые объекты, мип-уровни по просьбе.
Ошибка компиляции — `ShaderError` с логом и строками исходника вокруг ошибки (`formatShaderLog`), печатается
один раз; режим уходит на CPU.

**Потеря контекста.** `webglcontextlost` → `preventDefault` (иначе браузер не восстановит), программы и
текстуры забыты, состояние «потерян» — все эффекты перерисовываются по запасному пути. `webglcontextrestored`
→ программы соберутся заново при первом проходе, эффекты возвращаются на шейдер. Больше трёх потерь за сессию —
WebGL считается сломанным до перезагрузки. В истории «Потеря WebGL-контекста» это делает `WEBGL_lose_context`.

## Шаг 12. Новые режимы: что грузится и когда

`modes.ts` — лёгкая таблица: режимы, ячейки по умолчанию, у каких есть шейдер. Её и рантайм статически
импортирует компонент из основного входа кита. Ядра (`fx/kernels/*`) и рисующий слой (`render-extended.ts`)
грузятся через `import()` при первом кадре нового режима, шейдеры и общий контекст — ещё одной ступенью,
только если выбран путь WebGL. Пока чанк грузится, видна подложка, как при загрузке картинки; не загрузился —
обычное изображение.

Каждый режим — CPU-ядро на массивах RGBA; у семи (`crt`, `rgb-split`, `halftone`, `edge`, `thermal`,
`duotone`, `gradient-map`) есть шейдер с той же формулой. Это попиксельная работа на полном разрешении —
на GPU доли миллисекунды. Диффузия ошибки, сортировка и изолинии последовательны по своей природе, шейдер
им не помогает. Если проход шейдера не удался, кадр в тот же вызов считается на CPU.

Ячейка (`cell`) у каждого режима значит своё, а настройки — проп `options` (`modes.ts`,
`FilteredImageOptions`). Цвета — из той же шкалы краски темы, что у дизеринга (`inkRamp`, шаг 4).

## Шаг 13. `floyd`, `atkinson` — диффузия ошибки

`fx/kernels/error-diffusion.ts`. Пиксель берёт ближайший уровень шкалы краски, а ошибку (разницу) отдаёт
соседям, которых ещё не обработали. Флойд — Стейнберг: 7/16 вправо, 3/16, 5/16, 1/16 в следующую строку —
тона точные, но на ровных заливках бегут «черви», поэтому проход змейкой. Аткинсон (MacPaint): по 1/8 шести
соседям — раздаётся только 6/8 ошибки, света и тени «выгорают» в чистый цвет, узор чище и контрастнее, как на
экране первых Mac. В отличие от Байера узор зернистый и зависит от всего, что левее и выше.

## Шаг 14. `halftone` — растр

`fx/kernels/halftone.ts` и шейдер `HALFTONE`. Координаты пикселя поворачиваются на угол растра и делятся на
шаг (`cell`, 6 px) — видно, в какой ячейке пиксель и где её центр. Цвет берётся в центре ячейки (сетка
исходника на шаг растра, билинейно; у шейдера — мип-уровень), радиус точки `√краска · 0.71` (при полной
краске точка касается углов — растр сливается в заливку), край сглажен на пиксель. Линии — то же с
расстоянием до средней линии полосы. Цветной (`channels: 'cmyk'`): на светлой теме — четыре растра C, M, Y, K
под 15°, 75°, 0°, 45° (как в типографии — без муара), краски вычитаются из бумаги; на тёмной вычитание дало бы
чёрное пятно, поэтому там растры R, G, B складываются светом.

## Шаг 15. Тона: `duotone`, `gradient-map`, `thermal`, `posterize`, `threshold`

`fx/kernels/tone.ts`. Карта градиента: яркость → цвет шкалы (таблица на 256 уровней). `gradient-map` —
вся шкала краски темы, `duotone` — две её точки: смесь акцента с фоном в тенях и текст акцента в светах;
свои цвета — `options.colors` (токены `'--accent'` или CSS-цвета, читаются тем же пробным элементом).
`thermal` — научная шкала «холодное чёрное → фиолетовое → красное → жёлтое → белое горячее», тема её не
перекрашивает. `posterize` — каждый канал на `levels` ступеней. `threshold` — чистое ч/б по шкале краски;
порог по умолчанию — средняя яркость кадра, чтобы краски и пустоты было поровну на любой картинке.

## Шаг 16. `braille`, `dot-matrix`, `led`

**Брайль** (`fx/kernels/braille.ts`). Знак U+2800…U+28FF — сетка 2×4 точки, каждая точка — бит (столбец слева —
биты 1, 2, 3 и 7, справа — 4, 5, 6 и 8: нижний ряд добавили позже шеститочечного Брайля). Знакоместо даёт
восемь «пикселей» вместо одного у ASCII. Сетка исходника считается на точку (½ ширины и ¼ высоты
знакоместа), точка горит, если яркость выше порога Байера в своей клетке — полутона передаются. Почти
чёрное (ниже 6 %) — пусто, иначе тёмный фон фото покрылся бы редкой сеткой точек. Символы рисуются по одному:
если в шрифте нет Брайля, у запасного шрифта другая ширина, и строка целиком поплыла бы.

**Табло.** Цвет «диода» — ядро `ledPixels`: яркость на `levels` ступеней, выключенный диод слегка светится.
`dot-matrix` — одним цветом краски темы, `led` — цветом пикселя на полной насыщенности и всегда на тёмном
табло. Круги вырезает маска: плитка с кругом на ячейку через `createPattern` и `destination-in` — один
`fillRect` вместо тысяч `arc`. Ореол `led` — размытая копия (`ctx.filter = blur`), сложенная светом; где
`ctx.filter` нет (Safari до 18) — без ореола.

## Шаг 17. Экран: `crt`, `rgb-split`

`fx/kernels/screen.ts` и шейдеры `CRT`, `RGB_SPLIT`. **CRT**: бочка — точка рамки уезжает от центра на
`1 + k·r²` (k = 0.08), за краем кинескопа — фон; развёртка — косинус с шагом `cell`; маска люминофора —
вертикальные полосы R, G, B, чужие каналы на 60 %; свечение — тот же кадр, уменьшенный в 8 раз (у шейдера —
мип-уровень), в квадрате яркости, как у люминофора; виньетка к углам. **rgb-split**: красный сдвинут наружу
от центра, синий внутрь на `cell` px, к краям сильнее, как у линзы. Под курсором сдвиг втрое сильнее: у этого
режима `reveal` по умолчанию `finer`, а «мельче» для него значит «сильнее».

## Шаг 18. `pixel-sort`, `contour`, `edge`

**Сортировка пикселей** (`fx/kernels/pixel-sort.ts`): в каждой строке (или столбце, `direction:
'vertical'`) ищутся отрезки подряд идущих пикселей с яркостью в диапазоне `[threshold, 0.85]`, внутри
отрезка пиксели переставляются по яркости. Тени и блики стоят и держат рисунок, средние тона «стекают».

**Изолинии** (`fx/kernels/marching-squares.ts`): поле яркости на сетке `cell`, для каждого из `levels`
уровней — marching squares: клетка 2×2 узла классифицируется по тому, какие углы выше уровня (16 случаев), и
получает 0–2 отрезка с концами на рёбрах в точке линейной интерполяции — линия гладкая, а не ступенчатая.
Седловые клетки решаются по среднему значению клетки. Каждая четвёртая линия толще — как «утолщённая
горизонталь» топокарты. Рисуется без фона.

**Собель** (`fx/kernels/sobel.ts`, шейдер `EDGE`): градиент яркости ядрами 3×3 по x и y на шаге `cell`,
длина градиента → цвет шкалы краски. Ровное — фон, перепады — линии: фото становится «чертежом».

## Шаг 19. Проявление, линза, GIF и видео у новых режимов

Всё из шагов 6–9 работает и здесь: кэш кадров (в ключе — режим, путь рендера, `options`, свои цвета),
линза (`'original'` — оригинал, `'finer'` — ячейка вдвое мельче, у `rgb-split` — сдвиг втрое сильнее),
`data-effects`, reduced-motion, покадровые GIF и видео в переиспользуемых холстах. Отличие — проявление: у
растра, CRT или изолиний ячейка ×6 — другой рисунок, а не грубая версия того же. Поэтому кадр нового режима
считается один раз, а проявляется крупными пикселями готового кадра (уменьшить со сглаживанием → растянуть
без него, блок `max(4, cell) × 6 … × 1.6`).

Цена кадра (рамка 640×360, исходник 960×540, RTX 5070 через ANGLE D3D11; поток из 30 кадров, мс; скрипт —

## Шаг 20. Переходы между картинками — `ImageTransition`

Отдельный компонент во входе `@haunt/ui/fx`, а не проп фильтра: переход нужен и обычным картинкам, а у
фильтра своя жизнь кадра. `<ImageTransition src={cover} alt="…" />` — смена `src` запускает мягкий
переход от прошлой картинки к новой: `fade` (по умолчанию), `focus`, `reveal`, `wipe`.

1. Новая картинка декодируется (`img.decode()`) и один раз рисуется в размер рамки (cover) во внеэкранный
   холст; ядро масок (`fx/image-transition/transition-masks.ts`) грузится через `import()`.
2. `fade` и `focus` — без маски: прозрачность нарастает, а картинка чуть крупнее рамки «садится» на место
   (у `focus` ещё и размытие `ctx.filter` уходит в ноль; без `ctx.filter` — просто наплыв).
3. `reveal` и `wipe` — мягкая маска на сетке 160 клеток по длинной стороне. Порог клетки считается
   один раз: `reveal` — расстояние от центра, сбитое плавным шумом (расходится пятном), `wipe` — диагональ с
   лёгкой волной шума. Кадр: альфа клетки — плавная ступень по полосе вокруг порога (`fillMask`), маска
   растягивается **со сглаживанием** (`copy`), новая картинка ложится через `source-in` — край туманный, клеток
   не видно. Старая картинка всё это время — обычный `<img>` под холстом.
4. `data-effects="off"`, reduced-motion и `data-fx-renderer="static"` — смена мгновенная, без холста.

## Ограничения

- Источник должен разрешать чтение пикселей (свой origin, `data:`, `blob:` или CORS + `crossOrigin`).
- Смена `devicePixelRatio` без смены размера (окно перетащили на другой монитор) не пересчитывает кадр до
  следующего изменения размера.
- Анимированный GIF в Safari / WKWebView (Tauri на macOS) стоит на первом кадре: там нет `ImageDecoder`.
  Видео анимируется везде.
- ASCII на крупной рамке — самый дорогой режим покадрово (тысячи `fillText` на кадр): для фона лучше
  `dither` или `pixel`.
- Без WebGL растр, CRT, сдвиг каналов и табло на масштабе 2 стоят 20–80 мс на кадр (таблица шага 19):
  статичная картинка считается один раз, а видео и GIF по бюджету идут с меньшей частотой.
- Брайль опирается на знаки U+2800… в моно-шрифте; без них браузер берёт запасной шрифт, и точки чуть
  другого размера (сетка не плывёт — знаки ставятся по одному).
- Смена `src` у `ImageTransition` посреди перехода начинает новый переход от прежней показанной картинки.
